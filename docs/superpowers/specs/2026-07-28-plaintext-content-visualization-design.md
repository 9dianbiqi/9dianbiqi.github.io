# 博客 Plaintext 内容可视化与浅色代码卡设计

日期：2026-07-28

## 背景

博客已经具备全局 Mermaid 渲染能力，但旧文章中仍存在大量 `text` 和 `plaintext`
fenced code block。它们目前统一由 Shiki 渲染为深色代码框，因此两类本质不同的内容使用了
相同外观：

- 流程、架构、状态转换等关系型内容本应使用图表表达。
- 日志、目录树、路径、命令输出等字面内容需要保留原样，但不必使用沉重的深色代码框。

本次审计覆盖已发布文章，共发现 13 篇文章包含 84 个相关 fenced block，其中
25 个标记为 `plaintext`，59 个标记为 `text`。目标是一次性整理旧内容，同时形成今后
发布文章时可重复执行的内容规范。

## 目标

- 将旧文章中真正表达流程、架构、拓扑和状态转换的文本图手工改写为 Mermaid。
- 将日志、目录树、路径、配置、命令输出等字面内容统一为 `plaintext`。
- 为保留的 `plaintext` 提供与博客米白色编辑风格一致的浅色代码卡。
- 保持普通编程语言代码块原有的 Shiki 深色高亮外观。
- 消除旧的 `text` fence，避免同一种语义出现两种标记。
- 在 README 中记录可执行的判断规则，供后续文章发布沿用。
- 增加自动验证，防止旧标记和视觉规则回退。
- 在 1440、768、375 像素宽度下验证版式，并在发布前提供本地预览。
- 用户批准预览后，再由独立子 agent 执行远程发布和线上核验。

## 非目标

- 不把所有 `text` 或 `plaintext` 内容机械地转换为 Mermaid。
- 不在浏览器运行时根据文本内容猜测是否应该生成图表。
- 不改变 Python、JavaScript、Bash、JSON 等普通代码块的现有主题。
- 不为 plaintext 增加编辑器、行号、复制按钮或语法高亮。
- 不为 Mermaid 增加缩放、导出或交互式编辑功能。
- 不改写文章观点、技术结论或与可视化无关的正文。

## 采用方案

采用“人工语义分类 + 两种稳定表现”的方案：

1. 关系型内容在文章源码中直接改写为标准 `mermaid` fence。
2. 字面型内容统一保留为标准 `plaintext` fence，并由全局 CSS 显示为浅色编辑卡。
3. 构建和验证脚本负责检查标记与样式契约，但不负责猜测或改写正文。

这一方案使源码语义、网页表现和长期发布规范保持一致。与运行时自动识别相比，它不会因为
日志中恰好出现箭头或缩进而误生成图表；与全部保留代码框相比，它能让真正的流程关系更容易
阅读。

## 内容分类规则

发布或迁移时，按以下顺序判断。

### 转换为 Mermaid

满足以下任一条件时，使用 Mermaid：

- 有三个或更多具有业务含义的阶段，并通过箭头表达执行顺序或数据流。
- 存在分支、条件判断、回退、循环或状态转换。
- 表达系统组件之间的依赖、调用、部署拓扑或边界关系。
- 表达概念层级，并且层级本身比字面名称和路径更重要。

例如：

```text
请求 -> 策略检查 -> Agent -> 压缩 -> 评估 -> 持久化
```

应改写为：

```mermaid
flowchart LR
  request["请求"] --> policy["策略检查"]
  policy --> agent["Agent"]
  agent --> compression["压缩"]
  compression --> evaluation["评估"]
  evaluation --> persistence["持久化"]
```

### 保留为 plaintext

满足以下任一条件时，保留原始字面内容：

- 日志、命令输出、错误信息、响应示例。
- 文件系统目录树、Git 分支树或需要按原样复制的结构。
- URL、文件路径、文件名、日期范围、公式。
- 配置项、环境变量、接口清单、参数清单。
- 用户提示词、模板、检查清单或精确输入示例。
- 少量状态名称或优先级列表，但没有实际的状态转换关系。

即使文本包含 `->`、缩进或树形字符，只要读者需要的是原始文本而不是关系图，也不转换。

### 边界案例

- “目录结构”默认是 `plaintext`；只有展示逻辑模块归属而非真实路径时，才使用 Mermaid。
- “前端 / 后端职责”若只是文件清单，使用 `plaintext`；若表达请求如何跨边界流动，使用
  Mermaid 子图。
- 两个节点之间的一次简单映射通常保留正文或 `plaintext`，不为装饰而创建图表。
- 超长 Mermaid 图必须优先重构节点文案或改为自上而下布局，不能依靠页面级横向滚动。

## 旧文章迁移范围

迁移覆盖审计中发现相关 fence 的全部 13 篇已发布文章。重点转换对象包括：

- 飞书运维 CLI 的轮询链路。
- 账单治理的数据管线、隔离流程与状态分支。
- 动态看板的系统边界、目标架构与 Kubernetes 拓扑。
- 火山引擎账单模型的新旧架构。
- DeepResearch 的请求处理链路。
- 前后端并行开发中的分支切换与查询链路。
- 第三方 SSO 的浏览器、后端和第三方平台调用流程。
- SSO 指南中的登录、换票、鉴权和授权流程。
- VPN 指南中的隧道、路由决策和跳板访问关系。

其余日志、路径、目录树、配置和输出示例保留字面内容。实施时逐块复核，不以文件名或简单
正则批量决定类型。

## Plaintext 视觉规范

浅色 plaintext 卡沿用现有站点设计令牌：

- 背景使用暖米白表面色。
- 主文字使用墨色，标签和细节使用墨绿。
- 边框使用现有浅灰米色，左侧或顶部点缀可使用陶土色。
- 圆角、阴影和间距与文章中的图表卡片保持一致。
- 卡片显示低调的 `PLAINTEXT` 类型标签，帮助读者区分字面输出和正文。
- 使用等宽字体，保留空格、换行和制表结构。
- 长行仅在卡片内部横向滚动，不允许正文页面产生横向溢出。
- 不添加动画，悬停不改变内容可读性。

Shiki 会向 `<pre>` 和内部 `<span>` 写入深色背景及行内颜色，因此样式只针对
`pre[data-language="plaintext"]` 进行明确覆盖，包括必要的行内颜色覆盖。该覆盖不能影响
其他语言的代码高亮。

## Mermaid 视觉与失败回退

Mermaid 继续使用现有全局渲染器与站点主题：

- 浏览器端按需加载。
- 使用 `securityLevel: "strict"`。
- 成功时显示 SVG 图表。
- 渲染失败或 JavaScript 不可用时保留 Mermaid 源码。
- 宽图仅在图表容器内部滚动。

本次只改写文章中的输入内容，不改变 Mermaid 渲染器架构，除非验证发现现有实现无法承载
某个合法图表。

## 作者与发布契约

README 增加统一写作规则：

- 关系、方向、状态或拓扑使用 `mermaid`。
- 原样输出、日志、路径、目录树和配置使用 `plaintext`。
- 禁止新增 `text` fence。
- 普通代码必须使用准确的语言标记，例如 `python`、`bash`、`json`。
- Mermaid 节点含中文标点、括号或空格时使用带引号的标签。
- 发布前运行文章视觉验证和生产构建。

新文章发布时不进行运行时自动转换。作者或发布流程在源码阶段根据本设计完成分类，确保仓库
中的 Markdown 本身就是最终语义来源。

## 实现边界

预计变更集中在：

- 13 篇已发布文章的 fenced block。
- 全局文章样式中的 plaintext 定向规则。
- README 中的文章可视化规范。
- 文章视觉验证脚本及其测试入口。

不新增客户端 plaintext 脚本，不引入新的运行时依赖。Mermaid 依赖和启动脚本保持现状。

## 验证策略

实施遵循测试驱动开发：先增加能观察到失败的契约检查，再修改内容和样式。

### 静态验证

自动检查至少覆盖：

- 所有文章不再包含 `text` fence。
- 仓库仍存在经过分类后保留的 `plaintext` fence。
- plaintext 定向样式存在，并覆盖 Shiki 的深色背景和内部文字颜色。
- 普通语言代码块的样式规则没有被 plaintext 选择器扩大影响。
- README 包含 Mermaid 与 plaintext 的判断规则。
- 选定的代表文章包含预期 Mermaid fence。
- 现有 Mermaid 严格安全、动态加载和失败回退契约继续通过。

### 构建与回归

运行：

- `npm test`
- 文章视觉验证命令。
- Mermaid 专用验证命令。
- 现有相关 `verify:*` 命令。
- `npm run build`
- `git diff --check`

若仓库存在与本次无关的历史失败，必须单独说明，不能用它掩盖本次新增回归。

### 浏览器预览

在本地生产预览中抽查至少以下内容：

- 飞书运维架构文章中的轮询链路显示为 Mermaid，不再是黑色文本框。
- SSO、VPN、账单或动态看板文章中至少各抽查一个复杂图表。
- 日志、目录树和命令输出显示为浅色 plaintext 卡。
- Python、Bash、JSON 等普通代码块继续使用原高亮样式。
- Mermaid 渲染失败回退仍可见。
- 1440、768、375 像素宽度均无页面级横向溢出。
- 375 像素下长 plaintext 和宽 Mermaid 仅在各自容器内滚动。
- Astro 页面切换后图表继续正常渲染且不会重复初始化。

预览链接和代表性截图交给用户确认后，才进入发布。

## 发布流程

1. 在 `agent/plaintext-visuals` 分支完成内容、样式、文档和测试改造。
2. 完成本地构建、静态验证和多尺寸浏览器预览。
3. 向用户提供预览结果，由用户明确批准发布。
4. 按仓库约定，由独立子 agent 检查提交范围并执行提交、推送和 PR 流程。
5. 合并后等待 GitHub Pages 工作流成功。
6. 在线抽查 Mermaid 图表、plaintext 卡、普通代码块、首页和文章页。
7. Vercel 外部检查不作为 GitHub Pages 发布门。

## 验收标准

- 13 篇目标文章中的 84 个旧块全部完成逐块分类。
- `text` fence 数量为零。
- 符合关系型规则的内容已使用 Mermaid，且能在浏览器中成功渲染。
- 剩余字面内容统一为浅色 plaintext 卡。
- 普通代码块的现有视觉没有改变。
- 自动测试、生产构建和多尺寸预览通过。
- README 与验证脚本能够约束后续发布继续使用同一规则。
- 用户批准预览后，远程发布成功且线上表现与本地一致。
